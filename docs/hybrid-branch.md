# 旁路分支：从 `if turn < 7` 到按成本择路

## 0. 结论

原来那个 `if 会话次数 < 7: 跳过 KCCM` 的分支，方向对、判据错：

- 它用**轮次**做阈值，但真正的拐点由「每轮原文增量 ÷ 缓存固定成本」决定，不是固定的 7。
- 它让「跳过 KCCM」被理解成「不建缓存」，结果切换那一轮上下文从 332 骤降到 156、条目 8→0，模型直接失忆。
- 它把两条路当成互斥的静态选择，而实际应该**逐轮按成本选**。

改进后（`hybrid_mode=auto` + 死区 + 一步外推 + 桥接闸门 + 热缓存）的实测：

| 场景 | 全 KCCM | 固定7轮 | 自动（h=0） | **自动（h=.1+外推）** | 近2轮 |
|---|---:|---:|---:|---:|---:|
| normal（每轮增量≈40） | 2631 | 1832 | 1869 | **1832** | 1326 |
| dense（每轮增量≈90） | 4056 | 2991 | 3048 | **2985** | 2176 |

对比全 KCCM 省 30%（normal）/ 26%（dense）；对比固定 7 轮，normal 打平、dense 少 6 tokens，但**不需要事先猜 N**。

## 1. 原分支为什么会多花/白花 token

| 轮次 | 全 KCCM | 固定7轮 | 差值 |
|---|---:|---:|---:|
| T1 | 269 | 76 | −193 |
| T4 | 352 | 222 | −130 |
| T6 | 363 | 293 | −70 |
| T7 | 369 | 332 | −37 |
| T8 | 367 | 367 | 0 |

省下的钱几乎全在前 3 轮；到 T7 只剩 37 tokens 的优势，T8 归零。
**固定 N 的问题不是"省不省"，而是它把切换点钉死在一个与内容无关的数字上**——会话变密时太晚，会话稀疏时太早。

## 2. 改进后的方案

### 2.1 判据：按 token 择优，而不是按轮次

```
每轮同时渲染 raw(全量原文) 与 kccm(缓存)，取更省的一条。
```

- 本轮走 raw 时，缓存照常抽取、入库、跑 TTL/LFU（**热缓存**）。
- 不走 raw 时完全不渲染，没有额外开销。

### 2.2 候选集只放"信息完备"的两条路

截断窗口（近 2 轮）不进候选集。原因很硬：**纯按 token 最小择优会退化成"上下文越少越好"**，空上下文永远最便宜。
所以择优只在「全量原文」与「缓存」之间做，二者都声称掌握全部历史；窗口截断是信息损失，属于另一个维度的策略（`hybrid_recent`），必须由人显式选择。

### 2.3 死区 + 一步外推，必须配套使用

只用其中一个都会出问题：

| 策略 | normal | dense | 问题 |
|---|---:|---:|---|
| 死区 10%，无外推 | 1836 | 3070 | 拐点那轮只贵 1%，死区把它当成噪声，错过切换 |
| 外推，无死区 | 1869 | 3048 | 预测到下一轮会贵 4 tokens 就提前切，白付一轮 369 |
| **两者合用** | **1832** | **2985** | 不误伤、不错过 |

实现：`reference = max(raw_now, raw_now + (raw_now − raw_prev))`，只有当 `cached < reference × (1 − hysteresis)` 才切。

`raw_prev` 是上一轮的原文成本，增量外推假设"下一轮和这一轮一样长"。这个假设在答案长度稳定时成立，剧烈波动时会误判——所以死区不能设为 0。

### 2.4 桥接必须带成本闸门

切回缓存的首轮，附一次「上一轮原文」，用来接上指代链。但它是**机会性**的：

```
若 bridged.tokens <= raw.tokens 才附加，否则丢弃
```

实测桥接块约 40–80 tokens。normal 场景下 T8 的缓存是 367、原文是 371，桥接后 411 > 371，闸门直接把它拦下——**不能让"补上下文"把省下的 token 又吃回去**。

### 2.5 旁路期必须建缓存

`hybrid_skip_cache` 只保留给实验与测试，默认关闭。字面实现「跳过 KCCM 模式」会让切换轮缓存为空：

```
T7 原文 332 → T8 缓存 156（条目 8→0）→ 模型答"缺少可计算的数量"
```

省下的 211 tokens 不是收益，是把成本推给了后面的追问轮。

## 3. 配置项

| 参数 | 默认 | 说明 |
|---|---|---|
| `hybrid_mode` | `off` | `off` / `fixed`（按轮次）/ `auto`（按成本） |
| `hybrid_turns` | 6 | 仅 `fixed` 使用 |
| `hybrid_recent` | 0 | 旁路带几轮原文；0 = 全量 |
| `switch_hysteresis` | 0.10 | 死区；0 表示见便宜就切 |
| `hybrid_lookahead` | true | 一步外推；与死区配套 |
| `bridge_once` | true | 切回首轮补一次上一轮原文 |
| `hybrid_skip_cache` | false | **仅实验用**，会让切换轮失忆 |

推荐生产配置：

```yaml
hybrid_mode: "auto"
switch_hysteresis: 0.10
hybrid_lookahead: true
bridge_once: true
hybrid_skip_cache: false
```

## 4. 副作用与边界

| 副作用 | 影响 | 缓解 |
|---|---|---|
| 每轮渲染两次 prompt | CPU 翻倍，token 不变 | 只在 `auto` 下发生；可缓存渲染结果 |
| 两套模板并行维护 | 评测要做 2× 覆盖 | 共用同一 `SYSTEM_PROMPT` 骨架 |
| 外推基于线性假设 | 答案长度突增时提前切错 | 保留 10% 死区 |
| 桥接轮结构特殊 | 与其他轮不可比 | 评测按"桥接轮/非桥接轮"分层 |
| 择优不做质量评估 | 只保证"更省的上下文"，不保证"够用" | 需要离线评测集守住准确率下限 |

最后一条是这套方案的真实边界：**它优化的是 token，不是正确率**。在缓存退化（提取失败、槽位冲突）时，auto 仍然会选缓存，因为缓存确实更便宜。质量兜底要靠提取层的测试（`test_golden_apple.py`）与真实模型上的抽检。
