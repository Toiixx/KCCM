# 已知限制与适用边界

这份文档记录 KCCM **明确不解决**的问题。把它当作选型依据，而不是免责声明。

## 1. 槽位规则是手写的

`slot` 由 `src/kccm/extractor.py` 中的硬编码规则表生成，不是模型推断。

- **好处**：幂等、可测试、可解释，同一输入必得同一槽位。
- **代价**：换领域要扩 `src/kccm/data/lexicon.txt` 与槽位规则表。当前词表约 20 条，只覆盖"分东西/买东西"这一类场景。

若要做通用领域，需要把槽位判定换成可配置的 schema（如 JSON Schema + 规则 DSL），这已超出参考实现的范围。

## 2. 单槽位覆盖

同一槽位只保留一个 active 值。当用户说"可能是 3 个，也可能是 4 个"时，后一个会覆盖前一个，前一个进入 `superseded` 但不再参与推理。

不支持"同时持有多个候选值、按条件择优"。这是刻意的：多值槽位会让 prompt 与淘汰逻辑复杂一个数量级，而收益仅在少数场景成立。

## 3. 代词消解只做兜底

当前实现识别"纯指代"（整轮无新词、且含 `这/那/它/呢`），触发时把上一轮活跃集全部续命。这不是真正的指代链解析：

- 不区分"它"指代的是哪个实体；
- 不处理跨多轮的指代漂移；
- 不处理"前者/后者"这类结构指代。

## 4. 分词质量决定上限

`tagger.py` 有两个后端：

| 后端 | 何时启用 | 能力 |
|---|---|---|
| `JiebaTagger` | 安装了 jieba | 词性标注，能识别未登录名词 |
| `LexiconTagger` | 默认（零依赖） | 长词优先词典匹配，未登录词仅在 relaxed 模式下作为 OOV 候选 |

`LexiconTagger` 是**为了让 Demo 在无网络环境可运行、可测试**而存在的，不是生产级分词器。真实部署请安装 jieba，或换成你们自己的 NLP 管线。

## 5. 中文为主

英文按专名处理（`[A-Za-z][A-Za-z0-9._-]{1,30}`），不做词形还原、不做复数归并。日文、韩文未做适配。

## 6. 短会话不划算

固定开销（系统指令 + 结构化格式 + 槽位段）约 200–270 tokens。

实测交叉点在第 8 轮（`full` 模板）：少于 8 轮时，全量回放反而更省 token。**这个机制只在长会话中体现价值**。

## 7. 不适合长文档问答

KCCM 解决的是"多轮对话中事实遗忘"，不是"从 100 页文档里检索答案"。后者是 RAG 的问题域，需要向量检索或全文索引。混用两者通常两边都不讨好。

## 8. 不做的事

- 向量检索 / embedding
- 跨会话持久化（重启即清空）
- 多用户隔离与并发安全
- 工具调用与 function calling
- 对模型输出的忠实性校验（当前只校验"答得对"，不校验"没编造"）

最后一条值得单独说明：`RuleLLM` 是确定性计算器，不会编造；换成真实模型后，需要额外的**数值可追溯性校验**——抽取回答中的所有数字，若不在 `缓存 ∪ 本轮派生集` 内则标记 `unsupported_number`。这部分尚未实现。

## 9. 路线图

| 优先级 | 项 | 说明 |
|---|---|---|
| P1 | 数值可追溯性校验 | 回答中的数字必须能在缓存或本轮算式里找到出处 |
| P1 | 可插拔槽位 schema | 用配置替代硬编码规则表 |
| P2 | 多值槽位 | 支持"3 或 4"这类不确定陈述 |
| P2 | 英文适配 | 词形还原 + 冠词/介词过滤 |
| P3 | 持久化 | SQLite 快照，支持会话恢复 |
